# 重命名/移动检测 —— 设计

> 类型:设计规格 · 日期:2026-08-13
> 涉及:`searchidx`(`scan.rs` / `store.rs`)、`src-tauri/src/search/watch.rs`

## 0 · 一句话

用索引里**已经存着**的 `content_hash` 认出重命名与移动,只重算文件级元数据,不重算块 —— 而不是引入 Git 作为第二个「什么变了」的真相来源。

## 1 · 为什么

重命名、移动、删除**今天已经是正确的**:增量扫描每轮走一遍磁盘得到候选,再把「库里有、这轮没走到」的行删掉。GUI 的两条路径(watcher 与打开 vault)都不设预算上限,删除轮一定跑完。

问题不在正确性,在代价:**重命名被当成「删掉一个 + 来了个全新文件」**。`sweep` 按路径查已知行,新路径查不到就走全量索引 —— 重新读、重新分块、**重新分词**、**重新写 FTS**,哪怕内容一个字节没变。改一个装着 500 个转写稿的目录名,就是 500 次完整重建。

### 1.1 为什么不用 Git

用户最初的设想是让索引跟着 Git 识别到的动作走。四条理由否掉了它:

1. **时机对不上。** 用户在 Finder 里改名,watcher 立刻收到事件;git 要等 vault 自动同步提交之后才知道,而那是个带静默期的定时器。git 驱动会滞后数秒到数分钟,且**仍然需要 watcher 处理即时情况** —— 两套机制并存。
2. **未提交的改动 git 看不见。** 任何时刻工作区都有一批未提交编辑,而那是用户日常操作的大头。
3. **索引必须能在普通文件夹上工作。** 「文件高于应用」原则下 vault 不一定是 git 仓库;绑定 git 就要为非仓库场景留第二条代码路径。
4. **它引入第二个「什么变了」的真相来源。** 这个形状在近两个项目里坑了三次(盖章绕过唯一构造点、权重建好但无调用方、`sync_dir` 退休后四处注释仍在教它)。

而检测重命名所需的数据**索引里已经全有**:`files.content_hash` 每行都存,`store::all_file_rows` 每轮都把它连同 `mtime`/`size` 全量载入内存。

## 2 · 范围

**做:** sweep 与 watcher 批次两条路径的重命名/移动检测,共用同一个纯函数。

**不做:**
- 不做「重命名 + 同时改内容」的近似匹配。内容变了本来就要重建,没有损失。
- 不引入 Git。
- 不改删除、不改超时语义、不改 `index_one` 的单文件契约。

## 3 · 检测(规范性)

### 3.1 两个集合

| 集合 | 定义 |
| --- | --- |
| **新路径** | 磁盘上存在、且 `files` 里该路径没有行 |
| **孤儿** | `files` 里有行、但本轮没有被走到 |

两个集合在两条路径上都能得到:sweep 从整轮走查(`known` 减去候选路径集)得到;watcher 从一批事件里得到(批次内已不存在于磁盘且有行的 → 孤儿;存在于磁盘且无行的 → 新路径)。

**判断逻辑只写一份**,签名形如 `detect_renames(新路径集, 孤儿集) -> Vec<(旧路径, 新路径)>`,两处调用。

### 3.2 配对规则

1. **预筛:`(size, mtime)` 相等。** 无 I/O。POSIX `rename(2)` 与 Finder 移动都保留这两个值。这一步让「真正的新文件」在常见情况下不产生额外读 —— 不命中就直接走原有的全量路径,而那条路径本来就要读文件。
2. **确认:读文件算 `content_hash` 相等。**

**hash 确认不可省。** `(size, mtime)` 同时相等的两个不同文件是可能的(解压归档、一次 checkout 就能造出来)。配错的后果不是慢,是索引里出现「这个路径下是那个文件的内容」,而检索会拿着错的 `path#Lnnn` 回源 —— 这是整个设计里最不能破的契约。

3. **一个孤儿只能被认领一次。** 两个内容相同的新文件不能都声称来自同一个孤儿;第二个走全量路径。

## 4 · 快路径

配对成功后:**复用 `chunk::parse_file` 取其 `meta`、丢弃其 `blocks`/`links`**,然后一条 UPDATE。

**复用而非另写一个只算元数据的函数**,是刻意的:`origin`/`title`/`doc_date` 的推导规则是这个项目改动最频繁、且顺序有规范性的一块(见 `2026-08-12-source-globs-and-transcript-indexing-design.md` §3)。两条推导路径必然漂移。省下的分块开销远不如分词与 FTS 写入,而后两者已经省掉了。

### 4.1 更新哪些列

**路径派生,必须重算:**

| 列 | 为什么 |
| --- | --- |
| `path` | — |
| `ext` | `note.md` / `md` / `srt` / `vtt` / `txt`,`ext:` 过滤器要用 |
| `origin` | 规则 1 看 `.note.md` 后缀,规则 5′ 拿路径匹配原始资料模式 |
| `doc_date`、`date_inferred` | 优先取文件名的日期前缀 |
| `title` | 无 frontmatter title、无 H1 时回退到文件名主干 |
| `mtime`、`size` | 让下一轮 sweep 命中 stat 快路径 |

**内容派生,不动:** `content_hash`、`concept_type`、`tags_json`、`human_verified`,以及 `blocks` / `links` / `blocks_fts` 全部。后者正是省下来的大头。

### 4.2 两条必须退回全量重建的边界

**分块器类别变化。** `a.md` → `a.note.md` 内容一字未改,但前者走散文分块器、后者走大纲分块器,**块必须重算**。同理 `.md` ↔ `.txt` ↔ `.srt`。快路径的前提是新旧路径落在同一个分块器;否则退回全量。不挡住这条,「把笔记改名成手记」会留下用错分块器的块,而且测试全绿。

**目标路径已被占用。** 两个文件互换名字会撞 `files.path` 的 UNIQUE 约束。直接退回全量重建,**不为它设计临时路径腾挪** —— 罕见,而退路本身是正确的。

## 5 · 与删除轮的交互

`store::remove_file` 的四条 `DELETE` 全部按 `path` 匹配,而删除轮遍历的是 `known.keys()`(**旧路径**)。重命名后该行的 `path` 已是新值,所以那四条 DELETE 一条也匹配不到。

**数据安全,但统计会说谎**:`stats.files_removed += 1` 照加,日志会出现「删除 500 个」而实际一个未删。

因此:**已配对的旧路径必须显式从删除集合中摘除**,而不是依赖「DELETE 恰好匹配不到」。依赖巧合的正确性,在下一个人改动 `remove_file` 的匹配方式时就会破。

`ScanStats` 增加 `files_renamed`,并计入 `search` 分类的日志行 —— 否则「这轮什么都没重建」在日志里看不出是因为一切都是重命名。

## 6 · 不变的东西

- **超时语义不变。** 已完成的重命名是 UPDATE,已在同一事务内;超时仍整个跳过删除轮。
- **`index_one` 的单文件契约不变。** 重命名检测是跨文件的判断,只能在批次/整轮层面做。
- **watcher 配不上就退回原样。** 若 FSEvents 把一次重命名的删除与新增拆进两个 debounce 窗口,批次里只看得到一半,配对失败 → 逐个重建,即今天的行为。**这是降级,不是错误**,不需要为跨窗口配对设计状态。

## 7 · 测试

**前两条是核心:**

1. **重命名后 `path#Lnnn` 仍然指对。** 快路径的定义就是「不重算块」,所以必须端到端验:改名前搜到某行 → 改名后同一查询命中同一段文字、行号一致、路径是新的。
2. **改名进原始资料目录会改变分层。** `notes/a.md`(未标注)移入 `ebook/`(命中模式)必须变为原始资料 —— 证明元数据确实重算了,而不只是换了路径。

其余:

3. 分块器类别变化(`a.md` → `a.note.md`)退回全量重建,块按大纲分块器重算
4. 路径互换退回全量重建,不触发 UNIQUE 约束错误
5. `size` 与 `mtime` 均相同但内容不同 → hash 不匹配 → 不配对
6. 一个孤儿两个认领者,只有一个走快路径
7. `files_removed` 不把重命名算作删除;`files_renamed` 如实反映
8. watcher 批次同时含删除与新增时走配对;只含一半时退回逐个重建

**mutation 验证(必需):** 把 hash 确认短路成恒真,**第 5 条必须变红**;否则那条测试没有钉住任何东西。另外把「分块器类别相同」这个前提去掉,**第 3 条必须变红**。

## 8 · 残余风险

- **预筛依赖 mtime 被保留。** 若某个工具以「读旧文件 + 写新文件 + 删旧文件」实现移动,mtime 会变,预筛不命中 → 退回全量重建。正确,只是没省到。
- **跨 debounce 窗口的重命名配不上**(§6),同上:正确但没省到。
- **快路径省下的是分词与 FTS 写入,不是读文件。** 确认 hash 仍需读一遍。收益随文件大小上升,对一堆小 `.md` 不明显 —— 而真正的痛点(整目录转写稿)恰好是大文件,收益最大。
