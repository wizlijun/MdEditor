# 注意力加权检索 —— 设计

> 类型:设计规格 · 日期:2026-08-13
> 前置:`2026-08-11-md-origin-tiering-design.md`(origin 分层,已实现)、`2026-08-11-search-index-settings-design.md`(`Weights` 可配置,已实现)、`2026-07-08-reading-insights-design.md`(注意力数据的采集侧,已实现)

## 0 · 一句话

Reading Insights 已经逐日记下了你在每个文档上花掉的注意力时间 —— 那是「哪些文档对你重要」的一手证据,而检索侧至今一眼没看过它。把它接进索引,并让它随时间衰减。

## 1 · 为什么

origin 分层解决的是「这份文档是**谁**写的」,是一个类别级先验:`.note.md` 通常是你写的,所以整层 ×1.25。但它对同一层内的两份文档无话可说 —— 你反复读了三个月的那份 `Book`,和导进来就再没打开过的那份 `Book`,在索引眼里一模一样。

注意力时长是**个体级证据**,不是类别先验:它不猜你在乎什么,它记录了你在乎什么。而且它有类别先验拿不到的性质 —— **时效**。半年前读透的东西和这周天天开的东西,对「我现在要找什么」的指示强度差着量级。

CLAUDE.md 信念 1 说「你真正读过、标注过的文档,才赢得了你的注意力」。标注侧已经有 `is_annotation ×1.2` 在体现,**读过的那一半一直是空的**。

数据已经在磁盘上、已经跨设备 git 同步、已经按天分桶。这个项目基本是接线,不是造信号。

## 2 · 数据现状

`src/lib/insights/` 采集,落盘在 `<vault>/.notemd/analytics/YYYY-MM-DD.<deviceId>.json`:

- **docKey** —— vault 内文件是 `rel:<vault 相对路径>`(跨设备一致),vault 外是 `abs:<绝对路径>`(设备本地)。见 `model.ts` 的 `docKeyFor`。
- **每天每文档的计数器** —— `read_ms`、`edit_ms`、`open_count`、`edit_sessions`、`net_chars`、`mark_ops`、`first_seen_at`、`last_active_at`。
- 另有连续注意力区间 `sessions`(本项目不用)。
- 日期桶是**设备本地日**(`dayKey` 带 tz 偏移),所以跨时区设备的同一天可能错开几小时。对 30 天半衰期而言这是噪声,忽略。

已有的 `value.ts / valueScore` 是看板与日报的合成分,含受众阅读数据 —— 检索侧不复用它(见 §4.1)。

## 3 · 摄取:全量重算,不做增量

索引 DB 新增表,`SCHEMA_VERSION` bump(全量重建,索引是可弃派生物,既有正常路径):

```sql
CREATE TABLE doc_attention (
  path      TEXT PRIMARY KEY,   -- vault 相对路径,与 files.path 同域
  minutes   REAL NOT NULL,      -- 已衰减到 as_of 当天的注意力分钟数
  as_of     TEXT NOT NULL       -- 'YYYY-MM-DD';全表同一个值
);
```

摄取扫 `<vault>/.notemd/analytics/*.json`:

```
minutes(path) = Σ_days Σ_devices  (read_ms + 1.5·edit_ms)/60000 · 2^(-Δdays/30)
```

其中 `Δdays = as_of - 该文件的日期桶`。

### 3.1 为什么是全量重算

**当天的 analytics 文件整天都在被重写** —— 它存的是当日累计计数器,不是增量事件。任何「读到哪儿了」的水位方案都必须区分「这个文件变了但前缀没变」,做错就重复计数,而重复计数在这里是**静默**的:分数偏高,没有任何症状。Roam 增量同步当初为这类问题修了四处数据完整性 bug。

全量重算是无状态的:输出只由磁盘上的文件决定,不可能算错,也不需要迁移。

**成本靠截断封顶**:30 天半衰期下,365 天前的贡献是 `2^(-12.2) ≈ 0.0002`,低于任何有意义的精度。所以**只读最近 365 天的文件**,工作量上限 = 365 × 设备数 个小 JSON。这不是优化,是正确性边界的一部分 —— 没有它,vault 用十年后摄取成本会线性膨胀。

### 3.2 触发时机

- 索引打开时一次。
- `.notemd/analytics/` 内容变更后防抖 60 秒一次。

`.notemd/` 当前被 `is_indexable` 整体排除(`searchidx/src/scan.rs`,`.` 开头目录不进索引)。**这条排除不能改** —— 它挡的是 `.git` 的几万个对象。要做的是让 watcher 单独放行 `.notemd/analytics/` 这一个子目录,且只用于触发摄取,**不进 files/blocks**。

### 3.3 `abs:` key 归因到镜像副本

信念 4:「你的批注属于 vault,不属于路径」。你在 vault 外读一篇文章、批注后它被镜像进 vault —— 那段阅读时间记在 `abs:` key 下,而被索引的是镜像副本。不映射的话这份注意力永远兑现不了。

映射是**同设备内精确查表**,没有启发式:

```
analytics 文件名 → deviceId D
abs:<P> → metas.find(m => m.device_id == D && m.source == P)?.mirror
```

`MirrorMeta`(`src-tauri/src/sotvault/mirror_meta.rs`,存于 git 同步的 `.notemd/mirrors/`)带 `{mirror: vault 相对路径, device_id, source: 该设备上的绝对路径}`,而 analytics 文件名本身就带 deviceId —— 两边用的是同一个 `getDeviceId()` UUID。查不到就丢弃该条,不猜。

**必须按 deviceId 配对。** 不同设备上的 `/Users/x/notes/a.md` 是两个不同的文件;跨设备匹配 `source` 会把别人的阅读时间算到你的镜像上。

## 4 · 打分

### 4.1 成分:时长,编辑加权

```
minutes = (read_ms + 1.5 · edit_ms) / 60000
```

只有时间。**不计 `mark_ops`** —— 批注已经通过 `is_annotation ×1.2` 和 `origin=human ×1.25` 加过两道了,再摆进来是同一件事数三遍。**不复用 `valueScore`** —— 它含受众阅读数据(分享页的读者),而这个信号服务的是「我自己找我自己的东西」,别人读了多久与之无关;何况复用要在 Rust 重实现 TS 公式并用共享 fixture 钉死,成本换不来收益。

`edit_ms` 的 1.5 倍与看板 `DEFAULT_WEIGHTS.edit` 一致:写过比读过重。

### 4.2 衰减与加成

```
age_days        = today - as_of
m               = minutes · 2^(-age_days / 30)
attention_boost = 1 + k · min(1, ln(1+m) / ln(1+120))      -- k 默认 0.4
```

| 衰减后注意力 | 系数 |
| --- | --- |
| 0 min(从未打开) | ×1.0 |
| 5 min | ×1.15 |
| 30 min | ×1.29 |
| 60 min | ×1.34 |
| ≥120 min | ×1.40(封顶) |

**只加分,零注意力不惩罚。** `m=0 → ×1.0` 是硬约束,不是默认值。理由:AI 刚生成、你还没读的文档注意力恒为 0,而**你搜索的场合恰恰常常是去找它们**。惩罚未读等于把新产出永久埋掉,与信念 1 的方向相反 —— 信念 1 说「你投入过的更有价值」,没说「你没投入过的更没价值」。

**查询时再衰减一次(`age_days`)。** 表每天重算,但 app 开着一周不动时存量会冻住;这一项让陈旧的表优雅退化,而不是发出过期的高分。

因为**全表 `as_of` 相同**,衰减对所有行是同一个单调乘数 —— 所以候选阶段直接 `ORDER BY minutes DESC` 就等价于按衰减后排序,SQL 里不需要算指数。

### 4.3 接入 `score_of` 与 `Weights`

`Weights` 增加 `attention: f64`(即 k),默认 `0.4`。

**它的 `sanitized` 规则与其余四档不同,必须单独写:** origin 的四档是乘数,`0` 会让整层塌成 0 分、层内顺序变未定义,所以拒绝 0;而 `attention` 是加数,**`k=0` 恰好是「关掉这个功能」的正确表达**,必须放行。范围 `0.0..=2.0`,非有限值回落默认。

`k=0` 时 `score_of` 的输出必须与接入前逐位相同 —— 这是回滚开关,也是一条测试。

## 5 · 召回:第二条候选臂

`fts_search` 当前是 `ORDER BY rank ASC LIMIT (limit*8).max(64)`,**先按 bm25 取候选,再跑 `score_of`**。所以纯粹的排序加权只在候选窗口内重排:一份你读了三小时、但查询词只出现一次的长文,可能根本进不了窗口,再大的系数也救不了它。

「优先召回」要求在候选阶段就有它的位置:

```
候选 = FTS(… ORDER BY rank ASC              LIMIT limit*8)     -- 既有
     ∪ FTS(… ORDER BY f.minutes DESC, rank ASC  LIMIT limit*2)  -- 新增
        (按 block id 去重)
```

两臂**共用同一个 MATCH 条件**,所以新臂不引入任何不匹配的结果,只是让高注意力文档有机会走到评分阶段。`limit*2` 刻意取小:它是保底,不是主力 —— 主排序仍然是相关度。

`like_search`(`LIMIT 500`)与 `filter_only_search` 两条降级路径**不加臂**:它们已经是宽扫,截断压力不在那里,而 LIKE 路径本来就慢,不该再挂一条查询。

## 6 · 对外形态

- **UI** —— 本期不加可见标记,分组仍按 origin。顺序会变,呈现不变。
- **CLI** —— `--json` 每条命中增加 `attention_minutes`(衰减后的值,与 `origin`、`provenance` 并列),agent 可据此自行判断。扁平文本输出 `path:line:text` **不变**(前置 spec §5.1 的契约)。
- **查询过滤器** —— 本期不加。`attention:>30` 之类等有真实需要再说。
- **设置页** —— origin 分层统计容器旁增加一行:有注意力数据的文件数 / 索引内文件总数。这是发现「摄取根本没跑起来」的唯一途径。

## 7 · 测试

**摄取**
- 多设备同一文档合并求和;跨天求和。
- 365 天截断边界:第 365 天计入,第 366 天不计。
- `abs:` 经 mirror meta 归因到镜像的 rel 路径。
- **跨设备不串**:设备 A 的 `abs:` 路径不得匹配设备 B 的 meta,即使 `source` 字符串相同。
- 无 `.notemd/analytics` 目录 / 目录为空 / 单个 JSON 损坏 → 不报错,该条跳过,其余照常。

**衰减**
- 30 天前的 60 min 判定为 30 min(浮点容差内);90 天前判定为 7.5 min。
- `as_of` 陈旧 7 天时,查询侧的二次衰减确实生效。

**加成**
- `m=0` 严格 ×1.0(「只加分」的硬断言,不是近似)。
- 封顶生效:m=120 与 m=10000 系数相同。
- `k=0` 时全链路输出与接入前逐位相同。
- `Weights::sanitized` 对 `attention` 放行 0、拒绝负数与 NaN、上限 2.0。

**mutation 隔离** —— 沿用 origin tiering 的教训:注意力这一档单独失效时,必须**有且仅有**对应断言变红。前置项目出现过「两个乘数一起推同一方向、任一个单独失效测试仍通过」的假阴性,这里逐档隔离断言 `score_of` 本身,不靠端到端排序。

**召回臂** —— 构造一份 bm25 极低但注意力极高的文档,断言它在既有单臂下进不了候选、加臂后进得了;并断言新臂不会引入 MATCH 不命中的结果。

**回归集** —— 50 条 retrievability 全部重跑。任何期望值变更逐条人工确认后固化,**不允许照着新输出批量刷新**。与 origin tiering 一样,这是本项目最花时间的部分。

## 8 · 残余风险

- **富者愈富的正反馈。** 高注意力 → 排前 → 更容易被点开 → 更高注意力。对数阻尼、×1.4 封顶、30 天衰减三重限制了发散速度,但这是结构性倾向,不是能消除的 bug。若实测发现结果集僵化,先降 k,再考虑封顶下调。
- **注意力信号只在开过洞察的设备上存在。** `.notemd/analytics` 是 git 同步的,所以换设备历史还在;但从未开启洞察的用户这一档恒为 ×1.0,退化成现状 —— 可接受的空信号。
- **watcher 新放行 `.notemd/analytics/` 会引入新的抖动源。** 洞察 store 持续 flush,防抖不到位会让索引一直在忙。60 秒防抖 + 全量重算的固定成本是可预期的,但需实测确认不会撞上 v6.813.1 修过的「一直在构建、重建按钮消失」那类状态问题。
- **跨时区设备的日期桶错位。** `dayKey` 用设备本地日,同一时刻在两台设备上可能落进不同的桶。对 30 天半衰期是噪声,不处理。
- **注意力是本地派生数据,永不回写文件**(信念 2)。索引丢了重建,vault 里一个字节都不变;`.notemd/analytics` 始终是唯一事实源,`doc_attention` 是它的派生缓存。
