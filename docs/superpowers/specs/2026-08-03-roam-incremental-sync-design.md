# Roam 增量同步 — 设计

> 2026-08-03。在 `notemd.roam-import` 的当日同步之上加一层增量:记住上次同步的时间点,
> 每次只拉这之后真正变过的页面,日记页和 wikipage 各归各位。窗口与 CLI 同一条实现。

## 0. 背景与目标

`notemd roam-day` 只能同步**你点名的那一天**。日常真实的形态是:今天在 Roam 里改了三处,
其中一处是补写前天的日记,还新建了一个概念页。你不该需要逐个日期点一遍。

**目标**

1. 一个动作把「上次同步之后 Roam 里变过的所有页」拉进 vault。
2. 日记页进 `dailynote/yyyy/`,其余进 `wikipage/`,各带正确的 OKF `type`。
3. 水位持久化,下次继续增量;中断可续,不跳页。
4. 窗口与 CLI 各有入口,同一条实现。

**非目标(YAGNI)**

- 删除检测:Roam 里删掉的页/块,vault 保留 —— 与既有合并语义一致(§4 规则 3)。
- 全图重链:改名后指向旧名的 `[[wikilink]]` 会断;增量看不到全图,补不了。改名在报告里列出。
- 并发锁:窗口与 CLI 同时跑不加锁,靠既有的「写前重读、变了就中止」兜底。
- 反向写回 Roam。

## 1. 关键事实(本机实测)

**发现变更必须取两个维度的并集。** 这是本设计最容易做错的地方。

| 维度 | 查询 | 三天内命中 | 抓到什么 | 漏掉什么 |
|---|---|---|---|---|
| 块 `:edit/time` 的 max | `[?b :block/page ?p] [?b :edit/time ?t]` | 5 页(全是日记) | 内容修改 | **改名 / 建页**(块没动) |
| 页面实体 `:edit/time` | `[?p :edit/time ?t]` | 11 页 | 建页、改名 | **内容修改**(日记页此值≈创建时刻) |

实测证据:`08-03-2026` 的块最后编辑是 `2026-08-03T11:58Z`,而它的页面实体时间是
`2026-08-02T16:00Z`(东八区 00:00 建页那一刻)。反过来,`回顾系统` 等 7 个 wikipage
在 `2026-08-01T16:18Z` 有页面实体改动,块维度**完全查不到**。

⇒ **两条查询各跑一次,按 uid 合并,每个 uid 取两者较大的时间戳。**

其余已在当日同步中验证过的事实(递归 pull 形状、`:as` 别名必需、`{:block/children ...}`
不限层)见 `2026-08-03-roam-cli-daily-sync-design.md` §1/§3,此处不重复。

## 2. 台账 `.notemd/roam-sync.json`

存在 **vault 内**,与既有全量导入的 `.notemd/roam-import.json` 同一约定。

```json
{
  "graph": "bruce",
  "lastSyncedAt": "2026-08-03T11:58:41.185Z",
  "pages": {
    "8IFJWtnad":  { "path": "wikipage/回顾系统.note.md",            "title": "回顾系统" },
    "08-02-2026": { "path": "dailynote/2026/2026-08-02.note.md",   "title": "August 2nd, 2026" }
  }
}
```

**为什么放 vault 而不是设备本地**:`pages` 描述的就是 vault 里的文件,两者必须一致 ——
台账跟着文件一起走 git,才不会出现「台账说这个 uid 在 A 路径、A 路径却不在这台机器上」。
水位与它同生共死,所以放同一个文件。

多机并发同步会在这个 JSON 上产生 git 冲突。它是小文件、结构扁平,冲突可人工解;
真丢了也只是退化成一次全量重扫(所有页重新 merge,幂等,不损坏内容)。

## 3. 发现变更

```
A) [:find ?uid (max ?t) :keys uid edited :in $ ?since
    :where [?p :block/uid ?uid] [?p :node/title _]
           [?b :block/page ?p] [?b :edit/time ?t] [(> ?t ?since)]]

B) [:find ?uid ?t :keys uid edited :in $ ?since
    :where [?p :node/title _] [?p :block/uid ?uid]
           [?p :edit/time ?t] [(> ?t ?since)]]
```

`?since` 经 `--inputs '[<毫秒>]'` 传入,**在服务端过滤**(实测可用),返回集因此很小。

- `since` = 台账的 `lastSyncedAt`;**台账不存在时 = 本机本地时区的昨天 00:00**。
- 合并 A ∪ B,同 uid 取 `max(edited)`,按 `(edited, uid)` **升序**排 —— 升序是水位可续的
  前提,uid 次序键让同毫秒的处理次序可复现(§5)。

## 4. 逐页同步

每一页复用当日同步已有的 fetch → convert → merge → 原子写。**合并语义一行不改**:
按块 uid 对位、Roam 为准、本地手写块永不丢、内容无变化则连写都不写。

**落点与 OKF type**

| 条件 | 路径 | `type` |
|---|---|---|
| uid 形如 `MM-DD-YYYY` | `<daily_dir>/<yyyy>/<yyyy-MM-dd>.note.md` | `Daily Note` |
| 其余 | `<wiki_dir>/<sanitize(title)>.note.md` | `Wiki Page` |

`wiki_dir` 来自 `host.vault.info`(已有返回,后端目前只读了 `daily_dir`,本设计补上)。
`sanitize` 与全量导入同规则(非法字符 → `-`,去首尾空白与前导点,空则 `untitled`)。
type 取值与宿主 `outlineConceptType()` 的目录判定一致。

**跳过无块的页**:Roam 里 tag 会自动成页。没有任何块的页不建文件,计入 `skipped`。

**改名**:台账里该 uid 记录的 `path` 与本次算出的目标路径不同 → 先把旧文件 `rename`
到新路径,再在新路径上做合并写入。这样你写在里面的本地块、批注和 git 历史都跟着走。
旧路径不存在(被手工删了/移走了)就当新建。每次改名在报告里逐条列出。

**重名**:只有当目标路径被**另一个 uid** 占用(台账里查得到别的 uid 指向它)才追加 ` (2)`、
` (3)` 后缀,与全量导入同规则。台账记录带后缀的最终路径。同一次运行内后落位的页也按这条
规则避让 —— 台账在运行中逐页更新,所以判定始终看得到已落位的兄弟。

目标路径**在磁盘上已存在、但台账里无人认领**(你自己先建过 `wikipage/PKM.note.md`)时
**不加后缀**,直接按既有合并语义并进去:同一个概念本就该是同一篇,你写的块照例全部保留,
之后台账认领该路径。这与当日同步并入一篇已存在的日记是同一条规则。

## 5. 水位推进与可续

按 `(edited, uid)` 升序逐页处理(带 uid 是为了同毫秒时次序可复现),并更新该 uid 的
台账条目。遇到失败:停止,保留当前水位,把失败页计入报告。

**水位以「同一毫秒」为原子单位推进,不是每成功一页就推一次。**
持久化的水位 = 「小于本批失败页最小 `edited`」的最大 `edited`;本批无失败时 = 本批最大
`edited`。等价实现:只在组边界(下一页的 `edited` 严格更大)推进。

> **为什么不能每页一推**(原设计如此,已被证伪,勿回退):`edited` 不唯一 —— 批量编辑、
> 脚本导入,或两个发现维度撞在一起,都会让两个不同 uid 带同一毫秒 `T`。若 P 成功后就把
> 水位推到 `T`,而同为 `T` 的 Q 随后失败并中断,下次运行按 `> since` **严格**查询
> (§3;这个严格性必须保留,否则每次都会重同步上一页),`edited == T` 的 Q 落不进结果集,
> 于是**永久且无声地被跳过** —— 直接违背本功能「绝不跳页」的核心承诺。排序确定性救不了
> 它,病根在于把水位推到了一个不能唯一定位队列位置的值上。

水位也**只进不退**:`--since` 是人工补历史,让它把台账水位拨回过去会使随后的增量运行
凭空重扫一个月。

这样断网、Roam 关掉、进程被杀,下次运行自然从断点续上,**绝不会跳过任何一页**。
代价是失败点所在毫秒组及其之后已经查出来的页要重查一次 —— 幂等,无副作用。

⚠️ 水位取的是**页面的 edited**,不是 `now`。用 `now` 会把「扫描期间刚发生的编辑」一并
跳过,永久丢失那次修改。

## 6. 入口

**窗口**:CLI 区块内新增一个「增量同步」按钮,旁边显示上次同步时间(台账无记录时显示
「尚未同步过」)。与现有「同步当日」并存,状态互不干扰;三态 probe 的 `ready` 门槛相同。

**CLI**

```
notemd roam-sync [--since yyyy-MM-dd] [--dry-run] [--graph <name>] [--json]
```

- `--since` 覆盖台账水位,用于补历史;不传则用台账,台账无则昨天 00:00。
- `--dry-run` 只列出将要同步的页与目标路径(含将发生的改名),**不写盘、不动水位**。
- 退出码沿用 `roam-day`:0 成功;2 参数错;3 插件未安装;4 执行失败。

**报告**(UI 显示 / `--json` 输出)

```json
{ "from": "...", "to": "...", "scanned": 12, "synced": 9, "skipped": 2, "failed": 1,
  "renamed": [{ "uid": "...", "from": "wikipage/旧名.note.md", "to": "wikipage/新名.note.md" }] }
```

## 7. 测试

**Rust 单测**(纯函数,注入式,不起子进程)

- 两维查询结果合并:同 uid 取 max、只在 A、只在 B、两边都没有
- 分类:`MM-DD-YYYY` → daily;含非法字符的标题 → sanitize;空标题 → `untitled`
- 改名判定:台账 path 与目标不同 → rename;旧路径不存在 → 当新建;同 uid 路径不变 → 不动
- 重名:目标被别的 uid 占用 → ` (2)`;被**同一个** uid 占用 → 不加后缀
- 水位推进:全成功推到最后一页;中间失败停在**失败页所在毫秒组之前**(同毫秒的两页、
  后一页失败 → 水位必须低于该毫秒,且下次运行能重新看到这两页);空结果不动水位;
  `--since` 补历史不把水位拨回过去
- 台账读写:文件不存在、JSON 损坏、`pages` 缺失 → 各自的降级行为
- `--dry-run` 不写盘、不动水位

**集成测**(tempfile vault,注入假的「查变更」与「取页」闭包)

- 一次同步同时产出 daily 与 wiki 两类文件,各自 `type` 正确
- 改名后本地手写块仍在新文件里
- 连跑两次:第二次 `scanned` 为 0,文件与台账均无变化

**前端**:新按钮与新文案的四语言键齐全断言。

**GUI**:按仓库惯例由用户实机验证。

## 8. 验收

1. 首次运行(无台账)只拉昨天 00:00 之后变过的页,不是全图。
2. 一次运行同时正确产出一个日记页与一个 wikipage,`type` 分别是 `Daily Note` / `Wiki Page`。
3. 在 Roam 里给某 wikipage 改名 → 同步后 vault 里文件被**搬**到新名字,里面手写的本地块还在,
   报告里列出这次改名。
4. 断掉网络让中途失败 → 水位停在失败页所在毫秒组之前;恢复后再跑,失败那页(及与它同毫秒的
   兄弟页)被重新处理,更早的页不重复写。
5. 无变更时再跑:`scanned` 为 0,vault 无任何文件改动(git diff 干净)。
6. `--dry-run` 输出待同步清单,vault 与台账均无变化。
