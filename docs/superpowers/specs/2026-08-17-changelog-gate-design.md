# 增量 CHANGELOG 与发版门禁 —— 设计

> 类型:设计规格 · 日期:2026-08-17

## 0 · 一句话

每次发版都留下一段**人写的**变更说明,并让 `release.sh` 在没写时直接拦住发布。

## 1 · 为什么

至今没有 CHANGELOG。GitHub Release 的正文是 `gh api releases/generate-notes` 从提交自动生成的 —— 那是提交流水账,不是变更说明:它告诉你「合并了哪 41 个 commit」,不告诉你「这个版本对我有什么不同」。

v6.817.1 就是典型:41 个提交里,用户真正感知到的只有两件事(检索排序开始计入你的阅读时长;多了个 `notemd doctor` 自检命令),外加一件必须提前知道的(搜索索引会全量重建一次)。这三条在流水账里是找不出来的。

## 2 · 文件与格式

根目录两份,倒序:

- `CHANGELOG.md` —— 英文
- `CHANGELOG.zh-CN.md` —— 中文

与 `README.md` / `README.zh-CN.md`、`docs/FEATURES.md` / `docs/FEATURES.zh-CN.md` 的既有双语约定一致。

顶部固定一个「未发布」区,平时往里加条目;发版时它就地变成版本节:

```markdown
## 未发布

## v6.817.1 — 2026-08-17

### 新增
- …

### 修复
- …
```

约定:

- **条目面向用户,不是提交流水账。** 一条 = 一个用户能感知的变化,不是一个 commit。41 个提交可以合成 3 条。
- **类别只写实际有的**(`新增` / `修复` / `变更`,英文 `Added` / `Fixed` / `Changed`)。没有的组不留空标题。
- **需要用户提前知道的事(数据迁移、索引重建、破坏性变更)写在版本节最前面**,不塞进类别里。
- 版本标题格式固定 `## v<x.y.z> — <YYYY-MM-DD>`,两份文件逐字相同 —— §4 的漂移校验依赖它。

## 3 · 发版流程改动(`scripts/release.sh`)

**3.1 pre-flight 门禁**

两份 CHANGELOG 的「未发布」区都必须非空,否则 `die`,发布停在 pre-flight。

「非空」= 该区标题与下一个 `## ` 标题之间,存在至少一行非空白、且不是注释的内容。

**3.2 版本 bump 时轮转**

把两份文件的「未发布」标题就地替换成 `## v<version> — <date>`,并在顶部重新插入空的「未发布」区。两份文件随现有的 4 个版本文件(`package.json`、`Cargo.toml`、`Cargo.lock`、`tauri.conf.json`)一起进 `chore: release vX.Y.Z` 提交。

**3.3 Release 正文**

`gh release create --notes` 的正文改为:现有英文安装说明 preamble + `CHANGELOG.md` 里本次版本那一节。取代 `generate-notes`。

一处写作,两处到达。

## 4 · 防漂移

双语两份的老问题是漏改一边 —— 本项目已经因这类漂移出过事(`SEARCH_SECTION` 与 `templates/AGENTS.md`,靠 drift 钉子测试才逮到)。

门禁因此查两件事:

1. 两份的「未发布」区**都**非空(§3.1)
2. 两份的**版本标题序列逐一对应** —— 节数相同、版本号与日期逐字相同,不一致即 `die`

第 2 条挡得住「只更新了一边」。**挡不住翻译敷衍**(两边都写了但内容不对应),那只能靠人审 —— 这是双语方案自带的代价,明写在这里,不假装被解决了。

## 5 · 追溯

v6.817.1 已经发布,它的那一节是**补写**的,不走门禁。补写内容按 §2 的约定,从 `v6.813.6..v6.817.1` 的 41 个提交归纳。

## 6 · 测试

- **门禁**:「未发布」区为空 → 拦住;有内容 → 放行;只有一份非空 → 拦住。
- **漂移校验**:两份版本序列不一致(缺一节、版本号不同、日期不同)→ 拦住。
- **轮转**:替换后「未发布」区重新出现在顶部且为空;版本节标题格式正确;已有的旧版本节不被动到。
- **正文提取**:从 `CHANGELOG.md` 取出的是本次那一节,不含「未发布」区、不含上一个版本节。

这些是纯文本处理,用与 `scripts/release-plugins.test.ts` 同一套测试设施(Vitest)驱动,把逻辑抽成可导入的纯函数;`release.sh` 调用它,而不是在 bash 里现写正则 —— bash 的多行文本处理是这类脚本最容易出错、最难测的部分。

## 7 · 残余风险

- **门禁是硬的**:忘写 changelog 会卡住发布。这是刻意的,但意味着"急着发个 hotfix"时也得先写一行。可接受 —— 一行也是一行。
- **翻译敷衍挡不住**(见 §4)。
- **补写的 v6.817.1 是事后归纳**,不如当时写准确。往后每版实时写就没这个问题。
